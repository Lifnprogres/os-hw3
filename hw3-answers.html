(e) If a request in (c) led to an unsafe state, does that mean the processes would be deadlocked once it was granted? Explain the difference between unsafe and deadlocked, and describe a way the processes could all still finish from that unsafe state.

Unsafe means there is no completion sequence guaranteed if every process asks for its entire remaining maximum. Deadlocked means the actual outstanding requests prevent blocked processes from progressing now. An unsafe grant need not cause immediate deadlock. After granting P2’s request in (c), suppose P4 finishes without requesting its last claimed C unit: it releases (1,1,1), raising work from (3,2,0) to (4,3,1). P5 can then finish → (5,3,4), P1 → (7,4,7), P2 → (9,5,8), and P3 → (10,7,9). All finish. A claim is an upper bound, not a requirement to consume every unit.

The detection algorithm: (1) mark every process whose row of A is all zeros; (2) set the work vector W to the available vector; (3) find an unmarked process whose row of Q is at most W in every column (if several qualify, take the lowest-numbered); if there is none, stop; (4) mark it, add its row of A to W, and go back to step 3. Processes left unmarked at the end are deadlocked.

(a) Work out the available vector, then run the algorithm. Give every process marked, in order, with W after each mark, and name the deadlocked processes.

Allocated total = (1, 1, 2, 1), so available = (1, 1, 2, 1) − (1, 1, 2, 1) = (0, 0, 0, 0).
Step 1 marks P5 because it holds nothing; W remains (0, 0, 0, 0).
P4 has request (0, 0, 0, 0) ≤ W; mark P4 and add its allocation (0, 0, 1, 0): W = (0, 0, 1, 0).
P1 needs R2, P2 needs R1 and R4, and P3 needs two R3 units. None fits W, so stop. Deadlocked: P1, P2, P3.

(b) P5 is blocked waiting for R2. Is P5 part of the circular wait, or only blocked behind it? Why does the algorithm mark it in step 1, and what will happen to P5 once the deadlock is broken?

P5 is blocked behind the deadlock, not holding a resource needed to sustain its circular wait. Its allocation is zero, so marking it cannot release any units but correctly excludes it from the resource-holding deadlocked set. Once recovery lets P2 finish and release R2, P5 can receive R2 and proceed.

(c) The OS recovers by aborting deadlocked processes one at a time, least processor time used first, running the detection algorithm again after each abort and stopping as soon as no deadlock remains. An aborted process releases everything it holds and its request disappears. Which processes does it abort, in what order, and how much processor time is thrown away? Then find the fewest processes whose abort ends the deadlock. Which choice would you make, and why?

Initially P1 (3 s), P3 (5 s), and P2 (40 s) are deadlocked. Abort P1 first: available becomes (1, 0, 0, 0); P4 can release R3, making W = (1, 0, 1, 0), but P2 still needs R4 and P3 still needs two R3. Abort P3 next: available (1, 0, 0, 1); after P4, W = (1, 0, 1, 1); P2’s request (1, 0, 0, 1) fits, and releasing P2 gives W = (1, 1, 2, 1). No deadlock remains. Total work discarded = 3+5 = 8 s.
Fewest aborts: abort P2 alone. Its release gives (0, 1, 1, 0), then P1 finishes → (1, 1, 1, 0), P4 finishes → (1, 1, 2, 0), P3 finishes → (1, 1, 2, 1). This discards 40 s. I would choose P1 then P3 if discarded processor work is the main cost; it loses only 8 s, assuming no special external side effects or restart costs.

(e) Give one advantage and one disadvantage of running the detection algorithm at every request rather than periodically. Then explain how this algorithm differs from the banker's safety test: which matrix does each use, and why is detection called optimistic?

Checking every request detects a deadlock promptly, identifies the triggering request, and limits wasted work. It adds detection overhead to every allocation; periodic checks cost less but let deadlocks persist longer. Detection uses the current outstanding request matrix Q and allocation A. The banker uses maximum claim C minus allocation A (remaining possible need). Detection is optimistic because it allows grants without proving safety and assumes processes can finish after their current requests are met; it repairs an actual deadlock afterwards.

Problem 4The dining philosophers

Five philosophers, numbered 0 to 4, sit at a round table with one fork between each pair of neighbors. Fork i lies on philosopher i's left and fork (i + 1) mod 5 on the right, so philosopher 4's right fork is fork 0. A philosopher needs both of their forks to eat. A semaphore whose value is 1 works as a lock: semWait takes it (blocking while another holder has it) and semSignal gives it back.

semaphore fork[5] = {1, 1, 1, 1, 1};

philosopher(i):
    repeat forever:
        think();
        semWait(fork[i]);              // pick up the left fork
        semWait(fork[(i + 1) mod 5]);  // pick up the right fork
        eat();
        semSignal(fork[(i + 1) mod 5]);
        semSignal(fork[i]);

(a) Write a schedule (a list of steps such as "philosopher 2 picks up fork 2") that ends in deadlock. At the end, who holds which fork and who waits for which? Show how each of the four conditions appears.

Let philosophers 0, 1, 2, 3, 4 each pick up their left fork, respectively forks 0, 1, 2, 3, 4. Then each tries its right fork: 0 waits for 1; 1 for 2; 2 for 3; 3 for 4; 4 for 0. Each fork is exclusive (mutual exclusion); each philosopher holds one while requesting another (hold and wait); forks are released only by their holders (no preemption); the chain 0→1→2→3→4→0 is circular wait. All are blocked.

(b) A fix adds semaphore room = 4: each philosopher calls semWait(room) before picking up any fork and semSignal(room) after putting both down. Explain why deadlock is now impossible. What happens if room starts at 5 instead? What is the largest starting value that still rules deadlock out?

With at most four philosophers admitted, at least one seat is empty. The chain of philosophers holding left forks cannot cover the full ring: the philosopher just before an empty seat can acquire its right fork, eat, and release both. Thus no circular wait of all five forms. If room starts at 5, all can take their left forks and deadlock as in (a). The largest safe initial value is 4.

(c) Another fix leaves the original code alone except for philosopher 4, who picks up fork 0 first and then fork 4. Explain, using the idea of numbering resources, why no circular wait can form. Which of the four conditions does this fix rule out?

Philosophers 0–3 take forks i then i+1, and philosopher 4 takes 0 then 4. Every two-fork acquisition therefore takes the lower number first. A wait cycle would require strictly increasing fork numbers all the way around and then back to a smaller number, which is impossible. This rules out circular wait.

(d) Now the forks are interchangeable and sit in one pile in the middle of the table. A hungry philosopher takes forks from the pile one at a time and keeps any fork already taken while waiting for a second. What is the smallest number of forks in the pile that guarantees no deadlock for the five philosophers? Give the general rule for n processes that each need k units of one resource, taken one unit at a time, and use it for 8 processes that each need 3 tape drives.

Minimum = 5(2−1)+1 = 6 forks. With only 5, each could hold one and wait forever for a second. With 6, if nobody has enough to eat, the five can hold at most 5, leaving a fork to complete someone’s pair. In general n(k−1)+1 units guarantee progress; n(k−1) permits all n to hold k−1 and wait. For 8 processes needing 3 tape drives: 8(3−1)+1 = 17 drives.

(e) A different design lets a philosopher pick up forks only when both are free, taking the two together in one indivisible step. Explain why this design can never deadlock, and then describe a pattern of meals by philosophers 1 and 3 that could keep philosopher 2 hungry forever. What is the name for that problem, and how does it differ from deadlock?

Taking both forks atomically removes hold and wait: an unsuccessful philosopher holds neither. Philosopher 1 can begin eating while 3 still eats; 3 can next begin again before 1 finishes, repeating so at least one of forks 2 or 3 is always occupied. Philosopher 2 never gets both. This is starvation: other philosophers continue eating while 2 waits indefinitely. In deadlock, the involved processes cannot make progress at all. Fair admission would prevent starvation.

When the process next runs, how many times does its handler for SIGUSR1 run, and why? cv_wait releases the mutex and reacquires it before returning. (c) The module is loaded at 0x8000. What does each of the four words hold in memory with relocatable loading, and what would it hold with dynamic run-time loading at the same place? Relocatable loading adds the load base to the dictionary-listed address words only: 0x8000+0x0400=0x8400, +0x0388=0x8388, +0x0010=0x8010. The constant at 0x0040 must not change. Simply copying the relocated image to 0xA000 leaves stale pointers to 0x8000-based locations; the loader must relocate again (or adjust address words by 0x2000). (e) Using your answers to (d): about how much is wasted per process on average with pages of size p, and why do designers not simply choose very small pages? With roughly uniformly distributed final-page occupancy, average internal waste is about p/2 bytes per process (more exactly (p−1)/2 for integral byte lengths). Small pages reduce waste, but require more page-table entries and TLB coverage, and can increase translation overhead and small disk transfers. Paging is normally invisible to the programmer and uses fixed-size pages/frames, with internal fragmentation in the last page and no external fragmentation of frames. Segmentation follows visible logical units such as code, stack or a library; variable-size segments suffer external fragmentation. B-b Experiment 1, the deadlock. In your own words, say what each thread holds and what each waits for at the moment the detector runs. Then point to the line or lines of naive_transfer where each of the four conditions shows up: mutual exclusion, hold and wait, no preemption and circular wait. Why does the program use the barrier start_line, and what would you expect to see if that line were removed?

T1 holds account 0 and waits for account 1; T2 holds account 1 and waits for account 0. Mutual exclusion: with LOCKS[src] and the acquire of LOCKS[dst] allow one holder per account. Hold and wait: the thread remains inside the source with-block while trying LOCKS[dst]. No preemption: another thread cannot take the source lock away; the holder keeps it until it voluntarily exits the block. Circular wait: opposing src/dst plans create T1→T2→T1. The barrier start_line.wait() guarantees both source locks are held before either requests the other. Without it, one thread may acquire both and finish before the other starts, so deadlock becomes timing-dependent and may not be observed.

The detector uses cooperative rollback/resource release: set the victim’s give_up flag, let it return from naive_transfer, and release its first lock. It picks T2 because its planned payment is 50 rather than T1’s 100, treating it as cheaper to redo. No money has moved before both locks are acquired, so there is no balance update to undo; the missed T2 payment must be retried if wanted. The accounts become [400, 600, 500].
Ordered transfer acquires account numbers in ascending order (including 0 before 2 for the 2→0 payment). A payment ring therefore does not create a lock wait cycle. It eliminates circular wait; the programmer must enforce one global ordering at every acquisition site, sometimes differing from business-operation order. A total of 1500 checks conservation and catches lost/duplicated updates, though total alone does not prove that every individual payment or account is correct. The completed ring also restores [500, 500, 500].
